# ADR 0002: Шарова архітектура (layered architecture)

## Статус
Прийнято, 2026-09-16.

## Контекст
Обрано модульний моноліт (ADR 0001). Потрібні чіткі правила, що
зберігається в кожному шарі й куди можуть звертатись залежності,
щоб код не перетворився на "спагетті".

## Рішення
Три шари, кожен зі своєю відповідальністю:

- **`../../api`** — Express-роути. Приймають HTTP-запит, перетворюють
  тіло/параметри на прості об'єкти, викликають відповідний `../../service`,
  форматують відповідь і статус-код за контрактом з `docs/api/openapi.yaml`.
  Не містить бізнес-логіки.
- **`../../service`** — use-cases: валідація вхідних даних, виклик методів
  доменних об'єктів, координація роботи з репозиторієм (збереження,
  пошук). Мапить DTO ↔ domain.
- **`../../domain`** — сутності та їх інваріанти (з Практичної 3): `Order`,
  `Master`, `Payment` тощо. Не знає нічого про HTTP чи БД.
- **`../../repository`** (допоміжний шар) — зберігання доменних об'єктів
  (in-memory для тестів, SQLite для реального запуску). Ізолює
  `../../service` від деталей БД.

## Напрямок залежностей
```
api/  →  service/  →  domain/
              ↓
        repository/
```
Залежності йдуть тільки зверху вниз. `../../domain` ні від чого не залежить.

## Заборонені зв'язки
- `../../api` **не звертається напряму** до `domain/` чи до БД — тільки через `service/`.
- `../../service` не імпортує нічого з Express (`req`, `res`) — не повинен
  знати про HTTP.
- `../../domain` не імпортує нічого з `service/`, `api/` чи `repository/`.
